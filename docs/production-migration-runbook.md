# دليل تشغيل نقل قواعد Firestore إلى الإنتاج (drug-ordering-system)

> **الحالة:** وثيقة تشغيلية للقراءة والتنفيذ اليدوي عبر Firebase Console.
> **المرشح المعتمد:** `emulator-lab/firestore.rules`
> **SHA-256:** `1FA3C6076BBA8DA4F0E10138B9E61E62257943C3C689B01964F4EAB402CDC63B`
> **بوابة النشر:** النشر إلى الإنتاج يتطلب موافقة صريحة منفصلة — هذه الوثيقة لا تُفوِّض النشر.

---

## 0. هوية المشروع والأدوات
- معرّف مشروع Firebase: `drug-ordering-system` (يُتحقق منه في Console → ⚙ General → Project ID).
- كل الخطوات أدناه تُنفَّذ يدويًا من Firebase Console. لا تحتاج هذه الوثيقة أي أداة سطر أوامر.
- لا تُعطِ أي أسرار (مفاتاح API، رموز وصول) لأحد، ولا تُدخلها في المستودع.

## 1. تحقق ما قبل النشر (P0)
1. Console → Firestore → **Rules**: انسخ النص المنشور حرفيًا وقارنه بالنص الذي سلّمه المالك (القواعد المتساهلة) — يجب أن يتطابقان تمامًا (لا يكون هناك تغيّر مفاجئ).
2. تحقق أن المرشح المتجهز مطابق للبصمة أعلاه (ش PowerShell: `Get-FileHash .\emulator-lab\firestore.rules -Algorithm SHA256`).
3. تأكد من وجود **حسابين Google على الأقل** بصلاحية الوصول للمشروع (Console → ⚙ Users and permissions) مع تفعيل التحقق بخطوتين لكليهما. هذه هي ضمانة الاسترجاع الوحيدة.

## 2. تمهيد الحسابات الإدارية (قبل النشر مباشرة)
القواعد المرشحة **لا تسمح** بإنشاء مدير من داخل التطبيق إطلاقًا (الإنشاء مقيّد بـ `role:'employee'` و`status:'pending'`)، والتثبيت يتم **حصريًا من Console** (كتابات Console تتجاوز القواعد — خاصية منصة، لا تغيير للقواعد):

1. Console → **Authentication → Users**: أنشئ/حدد حساب الموظف المسؤول (بريد وكلمة مرور)، وانسخ الـ **UID**.
2. Console → **Firestore → users → Add document**:
   - **مسار المستند (Document ID) = الـ UID نفسه** (إلزامي: القواعد تقارن `request.auth.uid` بمسار المستند عبر دالة `isAdmin()`).
   - الحقول المطلوبة (شكل `users/{uid}` حسب `user-mapper.ts`):

   | الحقل | القيمة للمدير | القيمة للمساعد |
   |---|---|---|
   | `uid` (string) | = الـ UID | = الـ UID |
   | `name` (string) | الاسم المعروض | الاسم المعروض |
   | `employeeId` (string) | معرّف فريد (يُفضَّل عدم تكراره) | معرّف فريد |
   | `role` (string) | `admin` | `assistant` |
   | `status` (string) | `approved` | `approved` |
   | `hasException` (boolean) | `false` | `false` |
   | حقول `lastOrder*` | اتركها غير موجودة | اتركها غير موجودة |

3. كرّر نفس الخطوة للحساب الذي سيعمل مساعدًا (`role:'assistant'`).
4. **حساب `assistant@drugapp.internal`:** القواعد الجديدة تعتمد `role` من المستند فقط (لا فحص بريد). إن كان هذا البريد هو حساب المساعد الفعلي فامنح مستنده الحقيقي `role:'assistant'`؛ وإن لم يعد مستخدمًا فلا حاجة له (القواعد الجديدة لا تعرفه إطلاقًا).

## 3. مسار استرجاع المدير (لا يُضعف القواعد)
- القواعد المرشحة **لا تملك** مسار استرجاع داخليًا (بتصميم: الحذف محصور بالمدير، والإنشاء مقيد بالموظف).
- **الاسترجاع = Firebase Console**: أي حساب Google بصلاحية على المشروع يكتب/يعدّل `users/{uid}` مباشرة من Console متجاوزًا القواعد.
- الحد غير القابل للاسترجاع هو فقدان **كل** حسابات Google المخوَّلة على المشروع — لذلك يجب أن لا يقل عددها عن اثنين (بند 1.3).

## 4. تدقيق بيانات الإنتاج قبل النشر (P1) — قراءة فقط
افتح Firestore → **Collection queries** ونفّذ المراجعات التالية (المعايير مشتقة من شكل الحقول في الكود؛ أي قيمة غير متوقعة **تُحيل للمراجعة البشرية ولا تُفترض خبيثة**):

### users
- `role` خارج: `admin` / `assistant` / `employee`.
- `status` خارج: `pending` / `approved` / `rejected`.
- حسابات `admin`/`assistant` غير معروفة أو غير مصرَّح بها.
- حقل `uid` غير مطابق لمسار المستند.
- تكرار `employeeId`.
- حقول `lastOrder*` تناقض أحدث طلب للمستخدم في `orders`.

### medicines
- أرقام سالبة في `stock` أو `maxQuantity` أو `totalInward` أو `totalOutward`.
- `stock` لا يساوي `totalInward - totalOutward` (ملاحظة: تُراجَع الحالات يدويًا؛ قد توجد تعديلات مشروعة من تطبيق الإدارة).
- قيم غير منطقية صريحة (مثل `stock` بآلاف الوحدات دون سجل توريد).

### orders + stock_logs
- طلبات `userId` بلا مستند `users` مطابق.
- طلب بلا سجل `stock_logs` حاملًا نفس `orderId` (متوقع لكل طلب مُعالَج).
- سجلات تحيل إلى `orderId` غير موجود.
- `quantity` بعلامة سالبة أو مقدار غير منطقي.
- `actorUid` غير معروف في `users`.

### Authentication ↔ users
- قارن قائمة Authentication → Users بمستندات `users` (باستخدام الـ UID فقط، دون نشر بيانات شخصية): حساب Auth بلا مستند، ومستند بلا حساب Auth.

## 5. النسخ الاحتياطي والاستعادة
1. Console → **Firestore → Backups / Import and Export**: تحقق من وجود نسخة احتياطية مجدولة حديثة، أو أنشئ/جدول تصديرًا (Backup schedule) **قبل** النشر.
2. اختبر مسار الاستعادة وثّقه بتاريخه. غياب النسخة = مخاطرة مُعلنة واعية.

## 6. النشر (يتطلب موافقة صريحة منفصلة)
- **لا يُنفَّذ من هذه الوثيقة.** عند الموافقة: نشر الملف المعتمد نفسه دون أي تعديل، ثم فورًا:
1. تسجيل الدخول للديسكتوب بحساب المدير → ظهور الشاشات الإدارية.
2. تسجيل الدخول بحساب موظف → التأكد من ظهور شاشاته فقط.
3. تجربة إرسال طلب موظف ومعالجته (Stage 16/6) للتأكد من عودة مسار `order_requests` للعمل.
